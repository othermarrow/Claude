# 物音の多い録音の文字起こし(mojiokoshi)

NVIDIA の API(build.nvidia.com)だけで、録音を文字起こしする Termux 用のツール。
物音が声より大きい場面や、物音しかしない時間が長い録音を想定している。

- 物音しかしない時間は、スマホの中で声を検出して(Silero VAD)、**そもそも送らない**。
  送る量と時間が減り、Whisper が物音から文章を作る誤認識(「ご視聴ありがとう
  ございました」など)の大半を防げる。
- 声のある区間だけを NVIDIA API の音声認識(既定は Whisper large-v3)に送る。
- 返ってきた結果から、物音由来らしい誤認識を見分けて「除外」「要確認」に分ける。
  除外したものも末尾の一覧に残す(黙って消さない)。
- Whisper が区間の途中を飛ばしたらしい所(声の長さに比べて文字が少ない区間)は、細かく
  分けて送り直す。それでも文字にならなかった所は、本文に「(文字にならず)」と残す。
- 区間ごとに認識すると、前後を聞けば分かる言葉の取り違え(「反省会」が「反戦会」など)が
  残る。そこで LLM(NVIDIA API)に、聞き間違い・句読点・紛れ込んだ定型句だけを前後の
  文脈から直させた版を作る。方言・話し言葉はそのまま残させる。
- 結果は2つ。**md** は元の認識結果(時刻つき・要確認の理由と除外の一覧つき。音声と
  照らし合わせる用)、**txt** は LLM で整えた読む用(段落ごとに時刻・文ごとに改行)。

## しくみ

```
録音(m4a・mp3・wav・mp4 など)
 │ ffmpeg で 16kHz・モノラルに変換(80Hz 以下の振動・空調の音を切る)
 ▼
声の検出(Silero VAD・スマホの中)
 │ ① 元の音声 ② 雑音を除いて音量をそろえた音声(RNNoise → dynaudnorm)の両方で
 │   32ms ごとに「声らしさ」を出し、どちらかで声なら声とする
 ▼
区間分け
 │ 前後に 0.5秒の余白・2秒以内の区間はつなぐ(文脈が増えて正確になる)・
 │ 15秒を超える発話は声の途切れで分ける(長い区間ほど Whisper が途中を飛ばしやすい)
 ▼
送る音声を整える(区間ごと)
 │ 声のない瞬間の大きな物音(ドア・食器・叩く音)を声の大きさまで下げ、
 │ 声の音量をそろえる(遠くの小さな声も最大 +45dB まで持ち上げる)
 ▼
NVIDIA API で認識(Whisper large-v3・日本語。並列・送信間隔の調整・再試行つき)
 │ 声の長さに比べて文字が少ない区間は、7秒以下の片に分けて送り直し、
 │ 文字が多く取れた方を使う
 │ 同じ区間を、雑音を除いた音声(RNNoise)でももう1回認識する(2回目)
 │ (任意)確認用のモデル(parakeet など)でも認識し、食い違いを見る
 ▼
誤認識の見分け(物音由来の定型句・数え上げ・繰り返しを外す/要確認にする)
 ▼
md に元の認識結果を保存(2回目と中身が違う所は「別の認識」として並べる)
 ▼
LLM(nemotron-3-ultra など)が、1回目と2回目の認識を突き合わせ、聞き間違い・
句読点・紛れ込んだ定型句を前後の文脈から直して txt に保存
 │ 場面の説明と用語集(人名・専門用語)を渡せる。どちらの認識とも似ていない
 │ 書き換えは採らない。返答は JSON で受け取る
```

途中経過は録音ごとに `~/.cache/mojiokoshi/` に残る。途中で止まっても(Ctrl-C・
通信切れ・Termux が落ちた)、同じコマンドで続きから再開し、送った区間は送り直さない。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `mojiokoshi.py` | 入口。全体の流れ・再開・`models`・`check` |
| `config.py` | 設定(よく変える設定ほど上) |
| `audio.py` | 変換(ffmpeg)・声の検出(Silero VAD)・区間分け・送る音声の整え方 |
| `nvasr.py` | NVIDIA API(Riva の gRPC)の呼び出し。公式クライアントを使わずに通信する |
| `textfilter.py` | 誤認識の見分け |
| `output.py` | Markdown・テキスト(・SRT)の書き出し |
| `polish.py` | LLM で読みやすく整える(txt 用。`--no-polish` で切る) |
| `setup.sh` | 初回の準備(パッケージとモデル) |
| `update.sh` | 更新(Download の zip から入れ替え。モデルと設定は残る) |

公式の `nvidia-riva-client` は Termux ではビルドが要る依存(grpcio-tools)を持つため
使っていない。必要な通信の形(`riva_asr.proto` の一部)を `nvasr.py` で組み立てている。

## 準備(初回だけ)

1. このフォルダの zip(`mojiokoshi.zip` か、GitHub の `Code` → `Download ZIP` で
   保存した `Claude-ブランチ名.zip`)を Download に置く。
2. Termux で次を実行する。

```bash
termux-setup-storage
pkg install -y unzip
cd ~
mkdir -p ~/mojiokoshi_tmp
unzip -o -q "$(ls -t /storage/emulated/0/Download/mojiokoshi*.zip /storage/emulated/0/Download/Claude*.zip 2>/dev/null | head -1)" -d ~/mojiokoshi_tmp
mkdir -p ~/mojiokoshi
cp "$(dirname "$(find ~/mojiokoshi_tmp -name mojiokoshi.py | head -1)")"/* ~/mojiokoshi/
rm -r ~/mojiokoshi_tmp
bash ~/mojiokoshi/setup.sh
```

`setup.sh` は Termux のパッケージ(python・ffmpeg・python-numpy・python-grpcio・
python-onnxruntime)を入れ、声の検出と雑音除去のモデルを `~/mojiokoshi/models/` に
取ってくる(中身はハッシュで確かめる)。最後に `check` の結果が出る。

3. 短い名前で呼べるようにする。

```bash
cat >> ~/.bashrc <<'EOF'
alias moji='python ~/mojiokoshi/mojiokoshi.py'
alias mojiup='bash ~/mojiokoshi/update.sh'
EOF
source ~/.bashrc
```

4. API キーは `.bashrc` の `export NVIDIA_API_KEY=nvapi-...` をそのまま使う
   (research_bot の `~/.config/research_bot/keys.env` があれば、そこからも読む)。

5. モデルが使えるか確かめる(1分ほど)。

```bash
moji models
```

それぞれのモデルに雑音だけの短い音声を送り、`OK` / `NG` と、通った言語コード・
方式を表示する。通った組み合わせは `~/.config/mojiokoshi/functions.json` に残り、
次からはそれを使う。function-id が変わっていたら、ここで分かる(NVCF の一覧が
取れれば、名前から新しい function-id も探す)。

6. まず自分の声の短い録音(1〜2分)で試し、結果を確かめてから本番の録音に使う。

## 使い方

```bash
moji /storage/emulated/0/Download/録音.m4a          # 文字起こし
moji 録音.m4a --dry-run                              # 声の検出だけ(送信しない)。区間数と送信回数の見込み
moji 録音.m4a --from 1:00:00 --to 1:30:00            # 一部だけ(設定を試すとき)
moji 録音.m4a --verify parakeet                      # 確認用のモデルでも認識する
moji 録音.m4a --no-polish                            # txt を LLM で整えない(元の認識結果のまま)
moji 録音.m4a --vad-threshold 0.2                    # 声をもっと拾う(物音の誤検出も増える)
moji 録音.m4a --denoise rnnoise                      # 送る音声の雑音も除く(試すとき)
moji 録音.m4a -o /storage/emulated/0/Vault/文字起こし  # 保存先を指定
moji a.m4a b.m4a c.m4a                               # 複数をまとめて
moji /storage/emulated/0/Converter -o /storage/emulated/0/Converter/Output
                                                     # フォルダの中の音声をすべて
moji /storage/emulated/0/Converter -r -o /storage/emulated/0/Converter/Output
                                                     # サブフォルダの中まで
moji models                                          # モデルが使えるか
moji check                                           # 準備ができているか
```

### フォルダをまとめて処理する

録音ファイルの代わりにフォルダを渡すと、その中の音声・動画をすべて順に処理する
(wav・mp3・m4a・aac・flac・ogg・opus・amr・3gp・mp4 など。`.` で始まるファイルは飛ばす)。
最初に、見つけた件数と形式、処理の対象にした件数を表示する。

- `-r` … サブフォルダの中まで見る。保存先のフォルダ(`-o`)の中は見ない。保存先には
  サブフォルダと同じ構成で保存する(別のフォルダの同じ名前の録音がぶつからない)
- `--ext wav,mp3` … 拾う形式を絞る(大文字・小文字は区別しない)
- 同じ名前で形式だけ違うファイル(`録音.wav` と `録音.mp3` など)は、同じ録音とみなして
  1つだけ使う(wav → flac → m4a → aac → mp3 … の順で先のもの)
- 結果(`名前_文字起こし.md`)が保存先に既にある録音は飛ばす。新しく足した録音だけを
  処理するので、同じコマンドを何度実行してもよい。作り直すときは `--overwrite`
  (送った区間の記録が残っていれば、送り直さずに作り直す)

よく使うフォルダは、短い名前にしておくと楽。

```bash
cat >> ~/.bashrc <<'EOF'
alias mojiconv='python ~/mojiokoshi/mojiokoshi.py /storage/emulated/0/Converter -r -o /storage/emulated/0/Converter/Output'
EOF
source ~/.bashrc
```

### 録音のしかた(いちばん効く)

認識の精度は、録音そのものの声の大きさと雑音との差で大きく決まる。実際の録音
(3分23秒、変換アプリで作った mp3)を調べると、次のとおりだった。

| 項目 | その録音 | 目安 |
|---|---|---|
| 全体の音の大きさ | -50 LUFS | 会話の録音は -16〜-23 LUFS ほど |
| 声の大きさ | -50〜-68 dBFS | -20〜-30 dBFS ほど |
| 声と雑音の差 | 7〜25 dB(後半ほど小さい) | 20 dB 以上あると誤りが少ない |
| 形式 | 16kHz・モノラル・64kbps の mp3 | 録音アプリの元のファイル |

つまり声が普通の録音より 30dB ほど小さく(話し手から遠い)、後半は雑音とほとんど
差がない。このツールは小さい声を持ち上げて送るが、雑音も一緒に大きくなるので、
録音の段階で次のようにするのがいちばん効く。

- スマホを話し手の近く(1m 以内)に置く。ポケットや鞄の中、離れた棚の上は避ける
- 机に置くときは布などの上に置き、机を叩く音・物を置く音が直接伝わらないようにする
- 録音アプリに音質や感度の設定があれば、高い方にする
- mp3 などに変換せず、録音アプリが作った元のファイル(m4a など)をそのまま渡す。
  変換のたびに音質が落ちる(とくに小さな声の細部が消えやすい)。このツールは元の
  形式をそのまま読める

処理中は `termux-wake-lock` でスマホが眠らないようにし、終わったら通知する
(通知は Termux:API があるとき)。長い録音では、Android の設定で Termux の
「バッテリーの最適化」を外しておくと、途中で止められにくい。

### 時間の目安

この開発環境(Linux・x86)での実測。スマホではこれより遅いと見込まれる(未計測)。

| 段階 | 1時間の録音 |
|---|---|
| 変換と声の検出(2通り) | 約1分(実測) |
| 送信(声が2割・110区間の場合) | 2回目の認識を含めて約220回。送信上限 35回/分なら約7分(見込み。送り直しの分と、API の応答が遅い分は延びる) |
| txt の手直し(LLM) | 20区間ごとに1回。1回あたり数十秒〜1分半ほど(見込み) |

声の検出の結果は残るので、同じ録音のやり直しでは検出し直さない。検出を急ぐときは
`--fast-vad`(雑音を除いた音声での検出を省く。物音の下の声を取りこぼしやすくなる)。
送信を減らすときは `--single-pass`(2回目の認識をしない。送信回数が半分になる)。

## 出力

録音と同じフォルダ(`-o` か設定の `OUTPUT_DIR` で変えられる)に保存する。

| ファイル | 中身 |
|---|---|
| `録音_文字起こし.md` | 元の認識結果。区間ごとに時刻・文ごとに改行。処理の条件・要確認の理由・除外の一覧つき(音声と照らし合わせる用) |
| `録音_文字起こし.txt` | 読む用。LLM で聞き間違い・句読点・紛れ込んだ定型句を直した版。間の短い区間は1つの段落にまとめ、段落の頭に時刻、文ごとに改行。要確認の文は行末に「(要確認)」 |

txt を LLM で整えたくないとき(元の認識結果のままにしたいとき)は `--no-polish`
(いつもそうするなら settings.env に `POLISH=false`)。LLM が使えなかったときは、
txt にも元の認識結果を書く。

字幕形式(SRT)も要るときは、settings.env に `OUTPUT_FORMATS=md,txt,srt` と書く。
txt に時刻が要らないときは `TXT_TIMESTAMPS=false`。

md の本文の例(Obsidian では1行ずつ改行して表示される):

```
**00:12:34**
おはようございます。
今日は朝から雨が降っていますね。

*(00:13:10〜00:25:42 発話なし 12分32秒)*

**00:25:42** ⚠ 要確認: 物音だけでも出やすい言葉(声らしい部分 0.2秒)
はい。

**00:31:05** ⚠ 要確認: 声らしい音があるのに文字にならなかった(声らしい部分 3.2秒)
(文字にならず)
```

txt の例:

```
[00:12:34]
おはようございます。
今日は朝から雨が降っていますね。
食堂に行きましょう。

(00:13:10〜00:25:42 発話なし 12分32秒)

[00:25:42]
その件は、次の反省会で話しましょう。(要確認)
```

### 聞き間違いを減らす(場面の説明と用語集)

LLM で整えるとき、録音の場面の説明と、よく出る言葉・人名を渡すと、聞き間違いを
直しやすくなる。場面は settings.env の `POLISH_CONTEXT` に、言葉は
`~/.config/mojiokoshi/words.txt` に1行に1つずつ書く。

```bash
mkdir -p ~/.config/mojiokoshi
cat >> ~/.config/mojiokoshi/settings.env <<'EOF'
POLISH_CONTEXT=障害者支援施設の職員どうしの会話・会議。関西弁を含む
EOF
cat > ~/.config/mojiokoshi/words.txt <<'EOF'
反省会
強度行動障害
スケジュール支援
利用者
支援員
EOF
```

人名を書くと、文字起こしの文と一緒に NVIDIA のサーバーに送られる(下の「個人情報の
扱い」)。

### 誤認識の見分け方

| 扱い | 条件 |
|---|---|
| 送らない | 声らしい部分(声らしさがしきい値以上の時間)が合わせて 0.2秒未満の区間。物音で一瞬だけ声らしさが上がった所 |
| 除外 | 動画の字幕由来の定型句(「ご視聴ありがとうございました」「チャンネル登録」「字幕作成」など)だけの結果/効果音の表記(「(拍手)」「♪」)/同じ文字の繰り返しだけ/数を数え続けるだけ(「3 4 5 6 7 8 9 10」)/「ありがとうございました」「はい」など物音でも出やすい言葉だけで、その言葉を言い切れないほど声らしい部分が短い(1字 0.07秒・最低 0.5秒)/文字なし |
| 要確認 | 定型句・数え上げ(8個以上)を除いた残り/同じ語句の6回以上の繰り返し/声の長さに比べて文字が多すぎる/声の長さに比べて文字が少ない(送り直しても。抜けがあるかも)/声らしい音があるのに文字にならなかった/声の確からしさが低い区間/日本語以外の文字が多い/確認用のモデルでは声なし |

除外・要確認は、時刻・理由・認識結果を末尾の表に残す。消すのではなく、本文から
外すだけ。

## 設定

`config.py` は更新で上書きされるので、変えたい設定は
`~/.config/mojiokoshi/settings.env` に書く(更新しても残る)。

```bash
mkdir -p ~/.config/mojiokoshi
cat > ~/.config/mojiokoshi/settings.env <<'EOF'
OUTPUT_DIR=/storage/emulated/0/Vault/文字起こし
VAD_THRESHOLD=0.3
EOF
```

| 項目 | 既定 | 意味 |
|---|---|---|
| `OUTPUT_DIR` | 空(録音と同じフォルダ) | 保存先 |
| `OUTPUT_FORMATS` | md,txt | 書き出す形式(md / txt / srt) |
| `TXT_TIMESTAMPS` | true | txt にも段落の時刻を書く |
| `PARAGRAPH_GAP_SEC` | 3 | txt で、間がこれ(秒)より短い区間を1つの段落にまとめる |
| `POLISH` | true | txt を LLM で整える(`--no-polish` で一時的に切る) |
| `POLISH_CONTEXT` | 空 | 録音の場面の説明(LLM に渡す) |
| `GLOSSARY_FILE` | ~/.config/mojiokoshi/words.txt | よく出る言葉・人名(LLM に渡す) |
| `ASR_MODEL` | whisper | 文字起こしのモデル(whisper / parakeet / canary) |
| `VERIFY_MODEL` | 空 | 確認用のモデル(`--verify` と同じ) |
| `VAD_THRESHOLD` | 0.3 | 声とみなす確からしさ。下げると拾うが誤検出も増える |
| `VAD_DENOISED` | true | 雑音を除いた音声でも声を検出して合わせる |
| `DENOISE` | none | 送る音声の雑音除去(none / rnnoise / bnr) |
| `SPEECH_PAD_SEC` | 0.5 | 区間の前後の余白(秒) |
| `MERGE_GAP_SEC` | 2.0 | これ以下の間の区間はつなぐ(秒) |
| `MAX_SEGMENT_SEC` | 15 | 1回に送る長さの上限(秒) |
| `RECOVER_SHORT` | true | 文字が少ない区間を細かく分けて送り直す |
| `GAP_NOTE_SEC` | 60 | これ以上の無発話を本文に「発話なし」と書く(秒) |
| `REQUESTS_PER_MINUTE` | 35 | 1分あたりの送信上限。混雑の応答で自動で下げる |
| `CONCURRENCY` | 3 | 同時に送る数 |
| `AUDIO_STYLE` | auto | 音声の送り方(下の「うまくいかないとき」) |
| `POLISH_MODEL` | nvidia/nemotron-3-ultra-550b-a55b | 整えるのに使うモデル(使えない・応答しない状態が続くときは nemotron-3-super → gpt-oss-20b の順に切り替える) |
| `SECOND_PASS` | rnnoise | 同じ区間を雑音を除いた音声でも認識し、手直しで突き合わせる(none で切る) |
| `MAX_GAIN_DB` | 45 | 声の音量をそろえるときに足す音量の上限(dB) |
| `MIN_VOICED_SEC` | 0.2 | 声らしい部分がこれ(秒)未満の区間は送らない |
| `DELETE_AUDIO_CACHE` | true | 終わったら変換した音声を消す(結果の記録は残る) |

### モデル

| 短い名前 | モデル | 言語コード | 特徴 |
|---|---|---|---|
| whisper(既定) | openai/whisper-large-v3 | ja | 日本語の精度が高い。物音から文章を作ることがある |
| parakeet | nvidia/parakeet-1.1b-rnnt-multilingual-asr | ja-JP | 物音から文章を作りにくい方式。日本語の精度は未確認 |
| canary | nvidia/canary-1b-asr | ja-JP | 日本語に対応しているかは未確認(`models` で分かる) |

## うまくいかないとき

- **`API キーが通りません`** … `echo $NVIDIA_API_KEY` でキーが入っているか、
  build.nvidia.com でキーが有効か確かめる。
- **`function-id が見つかりません`** … `moji models` を実行する。NVIDIA 側で
  function-id が変わったときは、build.nvidia.com のそのモデルの API ページの
  `function-id` を見て、`moji models --set whisper <function-id>` で登録する。
- **`このモデルは指定の条件を受け付けません`** … 言語コードか方式が合っていない。
  `moji models` で通る組み合わせを探す。
- **すべての区間が空で返る** … 送り方が合っていない可能性がある。既定(`auto`)では、
  声のはっきりした区間が2回空で返ると WAV 形式で送る方式を試し、文字が返れば
  以降はその方式にする(`[送り方]` と表示される)。それでも空なら `moji models` と、
  短い自分の声の録音で確かめる。
- **会話が抜けている** … まず md の「⚠ 要確認」を見る。「文字が少ない」「文字にならな
  かった」と出ている所は、声はあるのに文字にできなかった所なので、音声で確かめる。
  表の「声と判定した時間」が実際の会話より明らかに短いときは、声の検出の取りこぼし。
  `--vad-threshold 0.2` で拾いやすくする(`--overwrite` を付けると作り直す。送った
  区間の記録は使い回すので、増えた区間だけ送る)。
- **物音を声と取り違えた区間が多い** … `--vad-threshold 0.4`〜`0.5`。
- **途中で止まった** … 同じコマンドをもう一度実行する。送った区間は送り直さない。
- **保存できない** … `termux-setup-storage` を一度実行して、ストレージを許可する。
- **txt が手直しされていない(「0区間を修正」)** … LLM の返答が読めなかったときは
  「返答のうち読めたのは…」と表示し、返答を作業フォルダ(`~/.cache/mojiokoshi/録音名-…/
  polish_reply_*.txt`)に残す。モデルを変えるときは `--polish-model nvidia/nemotron-3-super-120b-a12b`。
  4分以内に応答がない状態が2回続いたモデルは、自動で次のモデル(super → gpt-oss-20b)に切り替える。
- **作業フォルダを消したい** … `rm -r ~/.cache/mojiokoshi`(結果の .md・.txt は消えない)。

## 個人情報の扱い

声のある区間の音声は、NVIDIA のサーバーに送られる(物音だけの時間は送らない)。
txt を整えるときは、文字起こしの文(と、場面の説明・用語集)も NVIDIA の LLM に送られる。
build.nvidia.com の無料の API は、評価・試作向けの条件(NVIDIA API Trial Terms of
Service)で提供されている。利用者・職員の声や個人を特定できる内容を含む録音に
使う前に、規約の本文と、施設・自治体の個人情報の取り扱いの決まりを確かめること。

## 確認できていること・いないこと

実機で確認できていること:

- 利用者の Termux(Xperia 1 IV)で、Whisper large-v3 の API を使った文字起こしが
  1時間17分の録音で最後まで動いた(2026-10-15)。
- その結果から分かったこと: 物音が続く時間に、声らしい部分のごく短い区間から
  「ありがとうございました」「はい」などが約40行、数を数え続ける誤認識が2か所出た。
  関西弁・話し言葉・重なった会話では聞き間違いが多い。これを受けて、声らしい部分が
  0.2秒未満の区間を送らない・言い切れない長さの定型句を除外する・数え上げを見つける・
  LLM で整えた txt を作る、を加えた。その結果に新しい判定を当てはめると、物音由来
  とみられる 36行のうち 29行が本文から外れる計算になった(残り 7行は中身のある短い言葉で、要確認)。
- 3分23秒の録音で LLM の手直しを試したところ、「0区間を修正」となり、手直しが1つも
  入らなかった(返答を行番号つきの文で受けていて、その形が読めなかったとみられる)。
  返答を JSON で受け取る形に変え、読めなかったときは知らせて返答を残すようにした。
  同じ録音を調べると、声が -50〜-68dBFS と非常に小さく(上の「録音のしかた」)、
  送る前に足す音量の上限(当時 +30dB)では目安の大きさに届いていなかったため、
  上限を +45dB にした。

この開発環境(Linux)で確認できていること:

- 通信の形: 自前で組み立てた RecognitionConfig・RecognizeRequest・
  StreamingRecognizeRequest が、公式の `nvidia-riva-client` の定義とバイト単位で
  一致する。応答の読み取りも公式の定義で作った応答で確かめた。
- 手元の偽サーバー(Riva と同じ gRPC の形・function-id での振り分け・混雑の
  エラーをわざと返す)を相手に、変換 → 声の検出 → 送信 → 再試行 → 判定 → 保存、
  中断からの再開、確認用モデル(ストリーミング方式)、送り方の自動切り替え、
  キーや function-id の誤りでの停止、フォルダの一括処理(同じ名前の録音の重複を除く・
  済みを飛ばす・`--ext`・`-r` でサブフォルダと保存先の構成)が動いた。
- txt の整形: 偽の LLM サーバーを相手に、場面の説明と用語集・2回目の認識結果が
  指示に入ること、JSON の返答を読むこと、JSON の形の指定を受け付けないモデルでは
  外して送り直し行の形で読むこと、どの認識とも似ていない書き換え・欠けた行は元のままに
  すること、使えないモデルから次のモデルへ切り替えることを確かめた。応答しないモデル
  (時間切れ2回)から次のモデルへ切り替えること、思考を止める指定を受け付けないモデルでは
  外して送り直すこと、指示の末尾に行の数が入ることも確かめた(この3つは research_bot での
  同じ API の実測を受けて入れたもので、mojiokoshi の実機ではまだ起きていない)。返答の読み取りは、
  コードの囲み・前置き・途中で切れた JSON・番号が文字列・「番号 文」の形などでも試した。
- 2回目の認識: 雑音を除いた音声で全区間をもう1回送り、記録が別に残ること、1回目が
  文字にならず2回目が文字になった区間で2回目を使うこと、中身の違う所だけ md に並べる
  こと(2回目が定型句のときは並べない)を確かめた。
- 送り直し: 偽サーバーに「複数の発話を含む区間では最初の発話しか返さない」(Whisper が
  途中を飛ばすのをまねたもの)を設定し、細かく分けた送り直しで飛ばされた発話が戻ることを
  確かめた。実際の Whisper でどれだけ戻るかは確かめていない。
- 声の検出: 施設の録音に近づけたテスト音源3本(10分ずつ。合成音声と英語の実音声
  60発話を、ドア・食器・掃除機・水・咳・泣き声など ESC-50 の物音120回の中に、
  物音が声より 8〜12dB 大きく重なる場面も含めて配置)で評価した。
  - 元の音声だけで検出: 取りこぼし 15発話 / 物音だけの区間 10
  - 雑音を除いた音声と合わせる(既定): 取りこぼし 11発話 / 物音だけの区間 11
  - 取りこぼしは、声より 8〜12dB 大きい物音が重なった発話と、声より大きい掃除機の
    音の下の発話に集中した(人が聞いても聞き取りにくい条件)

確認できていないこと:

- JSON で受け取る形にした txt の手直しと、2回目の認識の突き合わせを、実際の LLM
  (nemotron-3-ultra など)で試すこと。どれだけ日本語として読めるようになるか、
  直しすぎがないかは、実際の録音で確かめる必要がある。
- parakeet・canary が日本語に対応しているか。
- BNR(`--denoise bnr`)。NVIDIA の公式クライアント(nim-clients の bnr.py)の
  ストリーミング方式に合わせたが、実際には試していない。失敗すると、雑音除去なしに
  切り替えて続ける。
- 声の検出と送り直しの設定が、実際の施設の録音でどれだけ効くか。テスト音源の声の
  多くは合成音声。
